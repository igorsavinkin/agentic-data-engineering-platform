# План коммуникации архитектуры — AI Data Platform

## Аудитория

Инженер / владелец проекта. Глубокое техническое понимание, необходимость
видеть полную картину: сервисы, потоки данных, границы ответственности,
статус реализации.

## Решенческий контекст

- Понимание текущего состояния платформы для планирования следующих milestone'ов
- Проверка архитектурной целостности: соблюдены ли заявленные границы сервисов
- Ориентир для onboarding новых AI-агентов и разработчиков

## Иерархия сообщений

1. **Что платформа делает** — event-driven конвейер конкурентной разведки
   e-commerce с медальон-озером (Bronze/Silver/Gold) и управляемым AI-агентом.
2. **Как устроена** — 6 сервисов, 5 Kafka-топиков, 3 слоя Parquet-озера,
   PostgreSQL как serving-слой, LangGraph-агент с read-only доступом.
3. **Что реализовано** — Milestone 0-3 (foundation, event platform, processing,
   data lake Bronze). Остальное — в roadmap (M4-M15).
4. **Ключевые ограничения** — at-least-once + идемпотентность, ingestion
   пишет только в Kafka, агент не пишет в БД.

## Выбранные виды

| Вид | Формат | Назначение |
|-----|--------|------------|
| Контейнерный вид | Graphviz DOT | Сервисы, хранилища, топики, границы ответственности |
| Поток данных | Graphviz DOT | Движение данных от источников до serving-слоя |

## Глубина объяснения

L2 (контейнеры/сервисы) с элементами L3 (модули внутри сервисов) для
ключевых компонентов. Технические термины без упрощений.

## Допущения и ограничения

- Диаграммы отражают **проектное состояние** (target), а не только реализованный код
- Реализованные компоненты: ingestion (placeholder), processor, raw-writer (Bronze), libs/common
- Нереализованные: lake-writer (Silver), warehouse-loader, API, agent, Airflow DAGs
- Kubernetes, Terraform, monitoring — placeholder-директории
